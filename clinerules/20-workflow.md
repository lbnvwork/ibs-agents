# Воркфлоу и статусы

- Конвейер: РП → Аналитик → Лид → Дев+Тест → Ревью(Лид) → Тест → Merge/DevOps. Полная схема: `docs/09-Служебное/Регламенты/Воркфлоу.md`. Колонки канбана: Надо делать → **Анализ** (Феб+Эйп) → Делаю → Ревью → Тестирую → Готово (+Отложено/Отменено).
- Статусы задачи: `spec → planned → in_progress → review → testing → deploy → done` (+`blocked`, `cancelled`).
- WIP: 1–2 задачи в работе на агента.
- **Docker: по завершении задачи останови свой стек** — `docker compose down` в своём каталоге. RAM на машине ограничена (критично), не держи контейнеры без надобности.
- **ЗАПРЕТ КОММИТОВ АГЕНТАМ (критично, без исключений):** агент не выполняет `git commit` — ни в коде, ни в документации (`ibs-docs`). Коммит — только руководитель (или РП по доверенности). Пуш — агент по отмашке руководителя (`ibs-docs` — свободно, без PR; `ibs` — в ветку + пулрек по отмашке).

## Отчёт вместо коммита (обязательный формат)
Полный отчёт агент пишет в «Комментарии» статьи задачи (docs). В чат руководителю — только названия коммитов; в чат РП — полный отчёт (при необходимости).

```
СДЕЛАНО:  <что сделано, кратко>
ФАЙЛЫ:    [код]  <путь в репо ibs>
           [docs] <путь в ibs-docs>
БЛОКЕРЫ:  <есть/нет + что именно блокирует>
КОММИТ:   [код]  <название коммита для ibs>
           [docs] <название коммита для ibs-docs>
           (жду отмашки — коммиты/пуш делаете вы)
ЗАМЕТКИ:  <опционально — важное, но не блокирующее>
```
- В чат руководителю: только `КОММИТ: [код] … · [docs] …`.
- В чат РП: полный отчёт (при необходимости согласовать решение).
- При необходимости — приложить `git diff`.

## Коммуникация руководитель ↔ агент
- Ответы/замечания/решения руководителя агентам — тоже в «Комментарии» статьи задачи, с `→ <агент>`.
- В личный чат агенту — только короткий пинг-триггер: «оставил замечания в комментариях к S.NN» / «закоммитил».
- Агент, получив пинг, обязан открыть статью задачи и прочитать комментарий руководителя.
- Это даёт единый журнал переписки по задаче (отчёты агента + решения руководителя) — скилл `status-briefing` читает его целиком.

## Статусы
- **Канбан** — единственный источник истины. **Двигает только РП** (скилл `sync-status`), атомарно, сразу после отчёта агента. Агент колонки не двигает — только отчитывается.
- **«План спринтов»** (планировщик) — обновляется РП **один раз в конце дня**, одним проходом.
- Не дублируй статус в 4 местах: статус живёт в Канбане, остальное — зеркала.
- Смена статуса — комментарием в статье задачи (`ДД.ММ.ГГ Кто: текст → кому`); пишет РП при движении карточки.
- **Ревью: замечания по коду — в PR** (inline/суммарно); в задачу — короткий статус («вернул на доработку, замечания в PR #N») + вердикт. Не дублируй подробности в задачу.
- Не раздувай задачу: существенная доработка = новая задача. Эскалация: Дев/Тест → Лид → РП → Руководитель.

## Перенос задачи в другой спринт — ЖЁСТКОЕ ПРАВИЛО (не забывать!)
**При переносе задача получает НОВЫЙ номер (код) целевого спринта.** Перенос без нового номера — ошибка процесса.
1. **Новый код** = `<спринт>.<следующий свободный NN>` (напр. `4.2 → 5.23`, `4.9 → 6.6`).
2. **Переименовать файл статьи**: `Спринт-04/4.2. Название.md` → `Спринт-05/5.23. Название.md`; заголовок `# N.N.` внутри статьи — тоже новый.
3. **Frontmatter**: `code`, `sprint`, `branch` (`5_23_...`), `depends_on` (ссылки на другие перенесённые задачи — на новые коды).
4. **Обновить все ссылки** на старый код: «Текущий спринт» (таблица переноса «Было → Стало»), «Детальный план» (целевой спринт + таблица переноса), «Общий план», зависимости в других статьях, статьи-разборы.
5. **«Текущий спринт»**: исходная строка помечается ⛔ с новым кодом («перенесена → 5.23»).
6. **Проверка перед отчётом**: `grep -rn '<старый код>' docs/` — старых ссылок быть не должно (кроме пары «Было → Стало»).
